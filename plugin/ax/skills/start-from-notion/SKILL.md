# 공고 → 프로젝트 기반 생성 (Notion 기준)

Notion **통합 사업 DB**(B2B/B2G 단일, "B2G 프로젝트 모니터링", `data_source_id=2e8ef4ce-ca2e-807c-b0b8-000b6bf3871a`)에서 **'제안 진행'으로 결정된 사업**만 골라 프로젝트 폴더·config·공고요약을 만든다.

## 핵심 원칙
- **Notion DB가 SSOT.** 사람이 DB에서 사업을 '제안 진행' 상태로 정하고 `사업성격`을 지정 → 이 스킬이 그 사업만 생성. **추측으로 사업을 만들지 않는다.**
- 폴더·파일 구조는 표준이 결정 → 사용자는 신경 쓰지 않는다.

## 1단계 — '제안 진행' 사업 조회 (Notion MCP)
`mcp__claude_ai_Notion__notion-query-data-sources` (SQL 모드)로 조회:
```sql
SELECT "사업명","발주기관","연도","사업성격","최종 지원 상황",
       "사업비 (VAT 포함)","공고 URL","date:최종 제출기한:start"
FROM "collection://2e8ef4ce-ca2e-807c-b0b8-000b6bf3871a"
WHERE "최종 지원 상황" IN
  ('수요기업 제안 준비','공급기업 등록 준비','전사 관점 제안 준비')
ORDER BY "date:최종 제출기한:start" DESC
```
> **트리거는 "제안 작업 진행 중" 3개만** (위 IN 절). `제안완료`·`공급기업 선정 완료`·`협약*`은 **이미 제안이 끝나 수주·수행 단계**로 넘어간 것이라 *신규 제안 폴더* 생성 대상이 아니다. 기존 진행 사업 합류는 별도(registry-sync). `미지원-*`·`탈락`·`지원 미정`·`홀딩`은 당연 제외.
- SQL 모드가 막히면(플랜 제약) "제안 진행 중" 뷰(`view://2ffef4ce-ca2e-8086-8f5a-000c9448246e`)를 `mode:view` 로 읽는다.
- 결과를 사용자에게 **마감 임박순 목록**으로 제시 → 어느 사업을 시작할지 고르게 한다(번호 선택).

## 1.5단계 — 데이터 정합성 점검 + 확인 게이트 (필수 — 사용자 무입력 보정)
**사용자가 상태 업데이트를 안 해서 생기는 불일치를 에이전트가 잡아 확인한다.** 조용히 건너뛰지 않는다.

선택된 사업에 대해 아래를 **결정론적으로** 점검하고, 위반 시 **생성 전에 사용자에게 확인**:

| 점검 | 규칙 | 불일치 시 확인 질문 |
|---|---|---|
| **마감 경과** | `최종 제출기한 < 오늘` 인데 상태가 제안 진행 | "이 사업 마감일(YYYY-MM-DD)이 지났어요. 상태가 안 바뀐 건가요? 그래도 만들까요?" |
| **교차 DB 상태** | 모니터링 DB '제안 진행'인데 상위/수주 DB는 '수주·수행·완료' | "모니터링엔 제안 중인데 수주실적엔 이미 수행 중이에요. 실제 단계가 뭔가요? phase를 수행중/완료로 바꿀까요?" |
| **사업성격 미입력** | `사업성격` 빈값 | "사업성격(B2G-용역/과제/B2B/내부)이 비어 있어요. 무엇인가요? (profile 결정에 필요)" |
| **중복 사업** | 같은 사업명이 이미 로컬 폴더/registry에 존재 | "이미 같은 사업 폴더가 있어요. 새로 만들까요, 기존에 합류할까요?" |

- 점검은 **상위 추진현황 DB**(상위 항목 relation)·수주실적 DB도 함께 조회해 교차 검증.
- **위반이 있으면 생성을 멈추고 사용자 확인**. 사용자가 답하면 그에 맞게 phase·profile 보정 후 진행.
- 위반 없으면 조용히 2단계로.

> 핵심: SSOT는 Notion이지만, **사람이 갱신을 빠뜨릴 수 있다.** 에이전트가 불일치를 근거(날짜·교차 DB값)와 함께 짚어 사용자가 바로잡게 한다. 추측으로 진행하지 않는다.

## 2단계 — 영문 폴더명 생성 (연도-기관약어-사업명)
선택된 사업의 필드로 **영문 슬러그** 구성:
- **연도**: `연도` 필드 (2026).
- **기관약어**: `발주기관` 값의 괄호 안 영문 약어 추출 (예: `예시기관(EXA)` → `exa`). 약어 없으면 기관명 로마자/핵심어.
- **사업명**: `사업명` 의 핵심 영문/키워드 슬러그 (한글은 핵심어를 영문으로, 길면 3~4단어). **사용자에게 슬러그를 1회 확인** (의미 손실 방지).
- 형식: `<연도>-<기관약어>-<사업슬러그>` (소문자·하이픈). 예: `2026-exa-proj-gamma`.

## 3단계 — 표준 기반 생성
> **권한 경계(v1.2)**: PM/PL 에이전트가 폴더·config·공고요약을 **직접 생성**한다 (사용자가 요청한 작업이므로 확인 불필요). 생성은 표준 골격·`init.sh` 엔트리포인트에 한정 — 임의 위치 쓰기 금지.

생성 대상:
1. **표준 폴더 골격** (마스터 `stage_dirs`·`support_dirs`):
   ```
   <폴더명>/
     .proj-sync/config.json
     reference/drafts/{00_영업_제안,10_착수,20_분석,30_설계,40_구현_시험,50_종료_인도}/   # 작업 초안
     reference/management/{risk,schedule,config,reports}/
     reference/_extracted/
     deliverables/        # 납품 Archive(최종본, 전부 git)
     revision/            # WBS·요구사항추적표 버전관리(작업)
   ```
2. **config.json** — 공고 8필드를 매핑:
   - `project.id` = 영문 폴더명, `project.name` = 사업명(한글 원본).
   - `lifecycle.phase` = 마스터 `phase_map['최종 지원 상황']` (제안 진행 3상태 → "제안"). 1.5단계 교차검증으로 실제 단계가 다르면 보정.
   - `wbs.profile` = `사업성격` → 마스터 `profile_map` 매핑 (B2G-용역→b2g, B2G-과제→b2g_rnd, B2B→b2b, 내부과제→internal).
   - 마감일 → wbs 기준 `due`, 사업비·발주기관·공고 URL → config 메타.
3. **공고요약 산출물** — `reference/drafts/00_영업_제안/공고요약.md`:
   - 발주기관·사업비·마감(D-N)·공고 URL·Notion 링크·사업성격. PM·PL이 즉시 참조.

## 4단계 — 다음 안내
- 생성 후 PM에게 "이 사업 지금 제안 단계, 마감 D-N, profile=○○. 다음 산출물은 제안요청서분석서·제안서" 안내.
- 원본 공고문서(hwp/pdf)는 Slack/Google Drive에서 받아 변환(`office_to_md.sh`) 후 `_extracted/` 에.

## 출력 (단순함)
- "○○ 사업 기반을 만들었어요. 폴더: 2026-exa-... / 지금 제안 단계, 마감 D-6."
- 약점·확인 필요(슬러그 적절성·사업성격 미입력 등)는 짚는다.
